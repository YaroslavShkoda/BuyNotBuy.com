# BuyNotBuy.com

Панель торговых сигналов по криптовалютам. Next.js 16 на фронтенде, Fastify 5
в `src/backend` — в этом же репозитории. Фронтенд обращается к бэкенду только с
сервера, из браузера к API напрямую не ходит.

## Требования

- Node.js **22.13 или новее**. Ниже этой версии `DatabaseSync` из `node:sqlite`
  доступен только за экспериментальным флагом, и сервис просто не запустится.
- npm 10+

## Быстрый старт

```bash
npm install
cp .env.example .env      # для разработки удобно MARKET_PROVIDER=mock

npm run backend           # http://localhost:3001
npm run dev               # http://localhost:3000
```

С `MARKET_PROVIDER=mock` данные детерминированы (`close = 100000 + i`), так что
результат не зависит от биржи и от времени запуска.

## Индикаторы

Периоды читаются из окружения при старте (`INDICATOR_*`) и проверяются: опечатка
даёт период `0` или `abc`, и без проверки индикатор молча соглашался бы сам с
собой, а каждый запрос падал бы в 500. Неверное значение останавливает процесс
с именем переменной в сообщении, а не всплывает позже.

**Подписи строятся из периода, а не пишутся в компоненте.** «ATR 14» — это
утверждение о том, что именно посчитано, и литерал в компоненте перестаёт быть
правдой в момент смены периода. Поэтому у каждого индикатора есть устойчивый
`key` (`ema`, `stochastic`, `momentum`), по которому его узнаёт интерфейс, и
ответ API содержит реально использованные периоды в `periods`.

Ключ нужен ещё и для истории. Таблица голосов адресована по индикатору, и если
бы она адресовалась по подписи, переименование начало бы новую серию и
оставляло все прежние голоса в старой — история молча разошлась бы надвое.

### Что голосует, а что нет

Голосуют **три**: EMA 300, Стохастик 100, Momentum 100. Именно они дают сигнал
и уверенность.

**ATR 14, RSI 14 и MACD 12/26/9 считаются и показываются, но в консенсус не
входят.** Это решение, а не ограничение: RSI почти повторяет Стохастик, MACD —
EMA 300, и три новых голоса выглядели бы как три новых подтверждения, не
добавив независимого свидетельства. Процент согласия вырос бы, а сигнал не
усилился бы. Вернуть любой из них в голосование — одна правка в
`calculateSignal`.

ATR хранится как доля от цены, а MACD — как подписанная доля, поэтому оба
показываются в процентах: «0.42%» значит одно и то же на любом инструменте,
тогда как «640» для BTCUSDT и для дешёвой монеты — разные вещи.

## Проверки
```bash
npm run verify              # линт + обе проверки типов + тесты
npm test                    # vitest, весь набор
npm run lint                # biome
npm run typecheck           # tsc по фронтенду
npm run typecheck:backend   # tsc по бэкенду
```

Линтер — [Biome](https://biomejs.dev), а не ESLint: `typescript-eslint` требует
TypeScript младше 6.1, а здесь TypeScript 7, и понижать его ради линтера не
стоило. Правила отобраны по дефектам (неиспользуемый код, `==`, `any`,
присваивание в условии, `!` в рабочем коде), а не по стилю: линтер, который
требует рефакторинга, мешает, и его начинают обходить. Исключения перечислены в
`biome.json` с объяснением — там четыре места, где правило неприменимо по
существу, а не «потому что так удобнее».

### Тесты не ходят в сеть

`src/backend/test-support/no-network.ts` подменяет `globalThis.fetch` на
отказ. Тест, который полез бы на биржу, проходит в хороший день и падает в
плохой, а падает он таймаутом не там, где ошибка. Единственный исходящий вызов в
репозитории — транспорт Binance, и он идёт через `fetch`, так что перекрыта
вся сеть.

Встроенные модули `node:` тоже подменяются, но это работает лишь наполовину:
именованный импорт ESM связывается при линковке модуля, и подмена
`require('node:http').request` уже не меняет связку, которую держит другой
модуль. Тесты на это не заявляют — надёжен только `fetch`, потому что он
разыскивается в глобальной области в момент вызова.

### Инварианты проверяются свойствами, а не примерами

`src/backend/properties/` — тесты на fast-check: генератор выбирает вход, а
тест утверждает правило. Остальные наборы описывают, как функция должна
работать, и не находят вход, о котором никто не подумал. Свойства сформулированы
так, чтобы контрпример был воспроизводим: fast-check печатает и сжимает его
до минимального.

Три из них пришлось переформулировать, потому что они утверждали не то:

- «курсор отвергается при любом изменении символа» — неверно, у base64url есть
  незначащие биты в последнем символе, и правка одного символа может не изменить
  байты. Правильное свойство: подделанный курсор не может указать на **другую**
  границу страницы.
- «сложение процентов не равно сумме» — на длинной цепочке доходы переполняются,
  и утверждение падало на собственном входе.
- «свеча с high ниже low отвергается» — при вычитании разрыва `high` уходил в
  минус и срабатывала проверка на отрицательную цену, то есть нужная проверка не
  выполнялась вовсе.

`.github/workflows/ci.yml`: линт, обе проверки типов, тесты и сборка на Node

## Сборка и запуск в продакшене

Бэкенд — обычная ESM-программа на Node. `tsc` собирает JavaScript, и Node
запускает его напрямую: в production не едет ни транспилятор, ни загрузчик, ни
исходники. `tsx` остаётся зависимостью для разработки.

```bash
npm run build             # next build + сборка бэкенда
npm run start:backend     # node dist/backend/server.js
```

`--env-file-if-exists` вместо `--env-file`: в контейнере конфигурация приходит
от оркестратора, и отсутствие `.env` не должно останавливать сервис.

Относительные импорты в бэкенде пишутся с расширением (`.js`) — этого требует
ESM-резолвер Node. Сборка использует `module: NodeNext`, и `tsc` падает, если
где-то расширение забыто.

## Docker

```bash
docker build -t buynotbuy-backend .
docker run --rm -p 3001:3001 \
  -e MARKET_PROVIDER=binance \
  -e APP_CORS_ORIGINS= \
  -v buynotbuy-data:/app/data \
  buynotbuy-backend
```

Образ многостадийный и не содержит зависимостей для разработки. Процесс
работает от непривилегированного пользователя, а `/app/data` объявлен томом:
база истории должна пережить пересоздание контейнера.

## Конфигурация

Все переменные перечислены в `.env.example` с пояснениями. Наиболее важные:

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `HOST` | `0.0.0.0` | С `loopback` сервис работает локально и молча недоступен в контейнере |
| `MARKET_PROVIDER` | `binance` | `mock` даёт детерминированные данные для разработки |
| `APP_CORS_ORIGINS` | пусто | Панель ходит в API с сервера, поэтому список origin по умолчанию пуст |
| `APP_TRUST_PROXY` | `false` | Включать только если впереди есть прокси, перезаписывающий `X-Forwarded-For` |
| `APP_REQUEST_TIMEOUT_MS` | `60000` | Должно быть больше худшего случая транспорта рынка |
| `HISTORY_DB_PATH` | `data/signal-history.db` | Путь ищется от корня проекта, а не от текущего каталога |
| `MARKET_POLL_ENABLED` | `true` | Выключать в разовых скриптах: таймер не даст процессу завершиться |

Переменные бэктеста (`BACKTEST_FEE_RATE`, `BACKTEST_SLIPPAGE_RATE`,
`BACKTEST_HOLD_BARS`, `BACKTEST_FOLD_BARS`, `BACKTEST_TRAINING_BARS`,
`BACKTEST_MAX_FOLDS`) читает только команда `npm run backtest` и на сервис не
влияют.

## Бэктест

```bash
npm run backtest
```

Печатает в консоль walk-forward отчёт: сколько сделок, прибыльных, итог,
максимальная просадка, профит-фактор и разбивка по окнам. Это команда, а не
эндпоинт: числа описывают поведение на прошлых свечах, и панель, которая их
показывает, подталкивает читателя к мысли, что бэктест — это прогноз.

Как устроено:

- **Сигнал в момент времени.** Индикаторы считаются только по свечам с
  открытыми по времени. Вход — на открытии следующей свечи, а не на закрытии
  той, что дала сигнал: закрытие известно только после того, как свеча
  закончилась. Тест на подглядывание переписывает будущее и проверяет, что
  прошлый сигнал не сдвинулся.
- **Окна вне выборки.** Каждое окно оценивается отдельно, пороги подбираются
  на предшествующем обучающем окне, а не на том, которое оценивается. Рядом
  печатается результат штатных порогов на тех же барах, иначе нельзя понять,
  помогла подгонка или нашла шум.
- **Издержки.** Комиссия и проскальзывание в обе стороны по умолчанию: биржа
  берёт 0.1% за сторону, и без этого любая метрика выглядит лучше, чем есть.
- **Сигналы, которые не стали сделками.** NEUTRAL считаются отдельно, иначе
  процент прибыльных ничего не значит: стратегия, которая молчит, когда не
  уверена, показывает блестящий результат именно потому, что пропустила сделки,
  на которых потеряла бы.

История для бэктеста берётся отдельно: Binance отдаёт максимум 1000 свечей за
запрос, поэтому провайдер догружает её постранично назад по времени. Живой
снимок на это не влияет.

Настройки прогона — через окружение:

```bash
BACKTEST_FEE_RATE=0 BACKTEST_SLIPPAGE_RATE=0 npm run backtest   # без издержек
BACKTEST_HOLD_BARS=6 npm run backtest                            # держать 6 свечей
BACKTEST_MAX_FOLDS=20 npm run backtest                            # больше окон
```

## Качество индикаторов

Консенсус — одно число, и оно прячет свои слагаемые: по нему нельзя понять, какой
из трёх индикаторов сигнал выработал, а какой просто попутчику. Поэтому каждый
голос пишется отдельно, и рядом считается, что рынок сделал через 1, 4 и 24
часа после него.

```bash
npm run indicators
```

Доходность знаковая по направлению голоса: верный SHORT считается таким же
плюсом, как верный LONG, иначе они взаимно сокращаются в среднем. За вычетом
круговых издержек 0.2% — прогноз, который не окупает исполнения, это убыток, а не
победа. Нейтральные голоса в процент попаданий не входят: индикатор, который
молчит, не получает ни заслуг, ни вины.

Горизонт заполняется только когда свеча, его закрывающая, уже появилась, поэтому
первые сутки после запуска таблица пустая — это ожидаемо. Команда доступна
только из консоли: в панели прошлый закрытый голос легко прочитать как
текущий, поэтому такие числа туда не выводятся.

## Наблюдаемость

| Адрес | Отвечает | Значит |
| --- | --- | --- |
| `GET /healthz` | 200 | процесс жив |
| `GET /readyz` | 200 или 503 | можно ли принимать трафик |
| `GET /metrics` | 200 | счётчики в формате Prometheus |

`/healthz` не проверяет ничего, кроме собственной готовности отвечать, и это
не осторожность: проба живости, которая спрашивает ещё и базу, перезапускает
процесс при падении зависимости, превращая сбой соседа в цикл падений и
уничтожая следы. Поэтому база проверяется в `/readyz`, где отказ означает «не
давать трафик», а не «убить».

Проба к провайдеру не проверяется нигде: его состояние меняется каждые секунды,
и проба, падающая на каждом чихе, выводила бы из строя работающий инстанс из-за
того, с чем сервис и так справляется — отдаёт последний годный снимок и
сообщает об этом заголовком.

`x-request-id` принимается от клиента, если он пригоден для журнала: без
перевода строки, без непечатных символов, не длиннее 128. Такой идентификатор
возвращается в ответе, чтобы клиент нашёл свой запрос. Непригодный не
отклоняется — иначе кто угодно, умеющий поставить заголовок, решал бы, работает
ли API, — а просто игнорируется.

Логи проходят через редактирование на выходе в приёмник, а не на каждом месте
вызова: мест десятки, и забывшее — это весь риск. Скрываются ключи, пароли,
токены и пароли внутри строк подключения, в том числе внутри исключений: там
они и приезжают. `Bearer` заменяется раньше остальных правил, иначе правило
«ключ=значение» остановилось бы на самом слове `Bearer` и оставило токен целиком
в логе.

Метрики считают по шаблону маршрута, а не по фактическому пути: путь содержит
символ и строку запроса, и по нему каждое новое значение создавало бы вечную
серию, а в каждой метке осели бы пользовательские данные.

## Контракт API

Ошибка, 404 и пустой ответ приходят одним и тем же конвертом
`{"error":{"code":"...","message":"..."}}`. Раньше неизвестный маршрут отвечал
собственной формой Fastify без поля `code`, и клиенту приходилось отдельно
обрабатывать ровно один адрес.

Разбор тела запроса отдаётся как ошибка клиента: битый JSON — это 400, а не 500.
Иначе виноватый в сбое оказывался сервер, и каждая опечатка в клиенте портила
счётчик отказов. Статус, взятый handler'ом изнутри, намеренно не повышается до
4xx: такая ошибка почти всегда наша собственная ошибка расчёта.

`GET /api/signal-history` принимает `cursor` и возвращает `nextCursor`:

```bash
curl "http://localhost:3001/api/signal-history?limit=24"
curl "http://localhost:3001/api/signal-history?limit=24&cursor=<nextCursor>"
```

Курсор непрозрачен и подписан, поэтому подделанный или обрезанный отклоняется
как 400, а не приводит к странице «откуда попало». Граница страницы — часть
запроса к базе, а не фильтрация в памяти. Сводка при этом всегда считается по
всей истории, а не по текущей странице: иначе «сколько держится сигнал»
зависело бы от того, сколько записей запросил клиент.

`GET /api/analysis` и `GET /api/market` отдают `ETag` и отвечают 304 на
`If-None-Match`. Тег анализа — **слабый**: в тело попадает `Date.now()`, и без
исключения этого поля каждый запрос получал бы новый тег, а клиент не увидел бы
ни одного 304. Заголовки свежести при 304 сохраняются — иначе клиент, не
получивший тело, не смог бы отличить «не изменилось и свежо» от «не изменилось,
но это повтор упавшего снимка». Политика кэширования остаётся у слоя свежести:
устаревший ответ помечается `no-store`, и условный запрос не имеет права это
отменить.

## Данные

История сигналов пишет фоновый опрос, а не обработчик запроса. Без этого
записи появлялись бы только при открытии панели, а метрика стабильности
измеряется в часах — дыры в истории читались бы как «сигнал не менялся».

База — SQLite в режиме WAL с `synchronous = NORMAL`. Версия схемы хранится в
`PRAGMA user_version`: база, написанная более новой сборкой, заставляет
текущую отказаться стартовать, а не тихо портить историю при первом запросе.

Тесты никогда не пишут в рабочую базу: `src/backend/test-support/test-database.ts`
подставляет временный путь до того, как модуль прочитает `HISTORY_DB_PATH` при
импорте. Иначе набор тестов, гоняющих настоящий `analyzeMarket`, оставлял бы в
`data/` выдуманные показания — цена 100 рядом с закрытием 100000, — которые
потом не отличить от измерений. Переопределить путь можно через
`HISTORY_DB_PATH` в окружении.
